# Webアプリ（PWA）で服薬を知らせることの限界

## 分かったこと
- Webアプリは、アプリを閉じている・画面がロックされている・別のアプリを前面にしているあいだは、音を鳴らし続けることができない。この間はプッシュ通知に頼るしかない（`public/js/alarm.js` の冒頭コメント）。
- ブラウザは、利用者が一度も画面に触れていないページでは音を出させない。そのため、アラームは「画面に触れた時点で鳴り始める」形にせざるをえなかった。
- カメラ・プッシュ通知・Service Worker は HTTPS でしか動かないため、動作確認は本番と同じ HTTPS の環境（Render）で行う必要があった。
- プッシュ通知の購読は端末（ブラウザ）単位でアカウントとは関係なく残るため、1台の端末を家族で共有する使い方では、通知が別の人に届く問題が起きた（`76bab28` で対応）。

## 考察
- アプリストアを通さずに配布でき、端末を選ばない点はWebアプリの長所だが、「確実に気付かせる」ことが求められる服薬アラームでは、ネイティブアプリより不利である。
- 本アプリでは「アプリ表示中は全画面アラーム」「閉じているときはプッシュ通知」「それでも記録がなければ家族へ飲み忘れ通知」と、手段を重ねることで弱点を補った。家族への通知は、利用者本人が気付かなかった場合の最後の安全策として位置付けられる。
- 今後の課題として、ネイティブアプリ化や、電話・SMS など別の手段での通知が考えられる。

## 記録の正確さと「あとからの訂正」
- 知らせる手段を重ねても、利用者が飲んだのに記録を付け忘れることは避けられない。その結果、実際には飲んでいるのに家族へ「飲み忘れ」が届き、記録上も飲み忘れが残る。
- そこで記録タブから、あとで付け忘れを登録したり、押し間違いを直したりできるようにした。一方で、あとから自由に書き換えられる記録は、家族や医療者から見た「証拠」としての信頼性が下がる。本アプリでは、訂正した時刻を「記録した時刻」として残し、予定時刻とは別に表示することで、いつ記録されたかが分かるようにした。
- 過去の日を訂正したときは家族へ通知しないことにした。通知は「いま起きたこと」を知らせるものであり、過去の訂正を知らせると誤解を招くためである。ただし、家族が訂正に気付きにくくなるという面もあり、訂正の履歴を残して家族が見られるようにすることは今後の課題である。

## 補足：「サーバーは送れたのに、スマホに表示されない」通知の原因の切り分け
- 「見守りの終了」の通知を追加したとき、PCで「見守りを外す」を押しても、見守る側のスマホに通知が表示されなかった。
- 最初は、送信時の緊急度（`urgency`）の違いを疑った。マイページのテスト通知は `urgency: 'high'`、ほかの通知は既定の `normal` で送っていたためである。`urgency` は、端末が省電力状態（Android の Doze など）のときに、すぐ届けるか後回しにしてよいかをプッシュサービスに伝える指定である。すべての通知を `high` にそろえ、`TTL`（端末がオフラインのあいだ保持する時間）も1日にした（古いお知らせが何日も後に届くと利用者が混乱するため）。しかし、これでは直らなかった。
- そこで、処理の段階ごとに確認用のログを入れ、Render のログで順に確かめた。
  1. 解除の要求がサーバーに届いているか → 届いていた（`DELETE ... 200`）。
  2. 通知を送る条件を満たしているか → 満たしていた。
  3. 送信先の端末が登録されていて、送信できたか → 1台に送信できていた。
- サーバー側は正常だったため、端末側の Service Worker（`sw.js`）を調べた。その結果、通知の表示で `renotify: true` を常に指定していたことが原因と分かった。Web の仕様では、`tag` が空のまま `renotify: true` を指定すると `showNotification` が `TypeError` になり、通知は表示されない。服薬の通知は記録のIDから `tag` を作るので表示されるが、記録に結び付かない「見守りの終了」やテスト通知は `tag` が空になっていた。
- 対策として、`tag` があるときだけ `renotify` を有効にした。
- 考察：
  - Web Push は「サーバーが送る」「プッシュサービスが届ける」「端末の Service Worker が表示する」の3段階に分かれている。サーバーのログで「送信できた」と出ても、利用者に表示されたことまでは保証されない。端末側のエラーはサーバーのログには残らないため、原因を見つけにくい。
  - 段階ごとにログを入れ、どこまで正しく動いているかを1つずつ確かめる方法が有効だった。推測で直そうとした緊急度の変更は、結果として原因ではなかった。
  - テスト通知も同じ理由で表示されていなかった可能性が高い。動作を確かめるための仕組みが、本番と同じ条件で動いているかも確認する必要がある。

## ネイティブ版（Android アプリ）を作って分かったこと（2026-11-12）
- 上の「今後の課題」のうち、ネイティブアプリ化に取り組んだ。Web の画面はそのまま使い、Capacitor で Android アプリに包んで、アラームの部分だけを Java で作った（`mobile/`）。
- Android では、Web ではできなかった次のことができた。
  - 目覚まし時計と同じ予約（`AlarmManager.setAlarmClock`）で、省電力状態（Doze）でも時刻どおりに動く。端末の再起動後も予約し直せる。
  - 通知の「全画面インテント」で、ロック中・画面が消えているときに全画面のアラームを出せる。
  - 「ほかのアプリの上に重ねて表示」の許可があれば、ほかのアプリを使っている最中でも全画面で出せる（全画面インテントだけでは、操作中は画面上部の小さな通知になってしまう）。
  - 通知に `FLAG_INSISTENT` を付けると、止めるまで音を繰り返せる。音は「アラーム」の音量で鳴る。
  - 一方で、これらはどれも利用者の許可が必要で、Android の版が新しいほど許可の種類が増え、設定画面の場所も機種によって違う。高齢の利用者が自分で4つの設定を済ませるのは難しく、マイページに「済み／設定する」の一覧を作って、設定画面へ直接案内するようにした。「確実に知らせる力」と「利用者に求める手間」の両立が、ネイティブ版での新しい課題になった。
- iPhone では、同じことはできない。iOS は、ほかのアプリの上に自分の画面を出すことを許していない。近いのは iOS 26 の AlarmKit（時計アプリと同じ形のアラーム）だが、表示は OS が決めた形になる。開発には Mac が必要で、本研究では Android だけで作った。OS ごとに「アプリにどこまで許すか」の方針が違い、同じ機能を両方で作れるとは限らないことが分かった。
- ネイティブ版の画面（WebView）は Web Push に対応していないため、家族への「飲み忘れ」通知はネイティブ版では受け取れなくなった（Firebase Cloud Messaging の追加で解決できる。`後でできるようにしたいこと/` に記録）。ネイティブ化で「できるようになること」だけでなく、「できなくなること」もある。
- 配布にも違いがある。Web 版は URL を伝えるだけで使えるが、ネイティブ版は APK を渡して「提供元不明のアプリ」を許可してもらう必要があり、ストアで配るには全画面アラームの権限について Google への申告が要る。
- 比較の方法（案）：Web 版とネイティブ版で、「服薬時刻から記録までにかかった時間」「アラームに気付かなかった回数」を測ると、ネイティブ化の効果を数字で示せる。
