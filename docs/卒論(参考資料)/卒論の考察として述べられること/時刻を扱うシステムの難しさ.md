# 時刻を扱うシステムの難しさ

## 分かったこと
- 本番のサーバーは UTC で動くため、日本時間との9時間のずれが、通知の時刻や「今日」の範囲の誤りとして現れた（`3ea7210` で `src/lib/jst.js` を追加して対応）。開発者のPC（日本時間）では再現しにくい不具合だった。
- 無料のサーバー（Render）はスリープや処理の遅れがあるため、「ちょうどその時刻に処理が動く」ことを前提にすると通知を取りこぼす。「時刻を過ぎていて、まだ処理していないもの」を対象にする設計に変えた。
- 「飲んだ」を押した時刻と、本来の服薬予定の時刻を区別しないと、同じ予定の記録が二重にでき、飲み忘れの誤通知につながった。
- お薬の時刻を変えた日には、「変更前の時刻の飲み忘れを残すか」「新しい時刻の予定を作るか」「通知を送るか」など、決めるべきことが多くあった（`c8ae8ea`, `6cef03d`, `cb7a9ff`, `e77d61c`）。

## 考察
- 服薬管理のように「いつ」が意味を持つシステムでは、時刻の扱いの小さな誤りが、家族への誤った飲み忘れ通知のような、利用者の信頼を損なう問題に直結する。
- 時刻の変換を1か所の関数にまとめ、記録の予定時刻をサーバー側で一意に決めることで、同じ予定が二重に扱われることを防げた。「誰が・どこで時刻を決めるか」を一本化することが重要だと分かった。
- 予定の変更や削除をしても、過去の記録（服薬済み・飲み忘れ）は消さずに残す方針をとった。お薬手帳として、記録は後から変わらないことが求められるためである。
