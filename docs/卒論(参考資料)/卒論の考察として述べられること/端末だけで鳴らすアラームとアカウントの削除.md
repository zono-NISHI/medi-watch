# 端末だけで鳴らすアラームとアカウントの削除

## 分かったこと
- 開発中に Supabase の SQL Editor で `DELETE FROM auth.users;` を実行し、アカウントをすべて削除したところ、ネイティブ版（Android）を入れたスマホで服薬アラームが鳴り続けた。スマホをタイムロッキングコンテナ（時間が来るまで開かない容器）に入れていたため、手で止めることもできなかった。
- ネイティブ版のアラームは、最後に取得した予定を端末に保存し、サーバーと通信せずに毎日予約し直して鳴らす作りになっている（`AlarmStore`・`AlarmScheduler`）。保存した予定が消えるのは、マイページで「ログアウト」を押したときだけだった。
- アプリがログインの無効に気づくのは、利用者がアプリの画面を開いてサーバーに問い合わせたときだけで、利用者が何もしなければ気づかない。サーバーから端末へ「止めて」と伝える手段もなかった。
- 詳しい対策の案は `docs/卒論(参考資料)/後でできるようにしたいこと/アカウント削除後に端末のアラームが鳴り続けないようにする.md` にまとめた。

## 考察
- 端末だけで鳴らす作りは、「通信できなくても、アプリを閉じていても知らせられる」という服薬アラームに必要な強みである。一方で、「サーバー側の変更（アカウントの削除）が端末に届かない」という弱点にもなる。同じ設計が利点と欠点の両方を生むことが分かった。
- 服薬アラームには、「止めるべきとき（アカウントの削除）は確実に止める」と「止めてはいけないとき（通信の不具合・ログインの期限切れ）は止めない」の両立が求められる。ログインが切れただけで黙ってアラームを止めると、高齢の利用者が気づかないまま飲み忘れが続くおそれがあるため、単純に「ログインが無効ならアラームを消す」とはできない。
- 多くの人が使うシステムでは、アカウントの削除を決まった手順だけで行い、サーバーから端末への知らせ（FCM のデータメッセージ）と、端末からサーバーへの定期的な確認を組み合わせて、何重にも備えるのが一般的である。開発の都合で SQL から直接データを消す操作は、こうした後始末を飛ばしてしまう。
- アカウントを消しても端末にお薬の名前が出続けることは、利用者の混乱だけでなく、個人情報の扱いの問題にもつながる。データを「消す」ことの設計は、作る・表示することに比べて見落としやすい。

## 対策を作ってみて分かったこと（2026-11-26 追記）
- 対策は「サーバーから端末へ知らせる（FCM）」と「端末からサーバーへ確かめる（鳴らす前・アプリを開いたとき）」の両方で作った。前者だけでは、SQL で直接アカウントを消した場合（今回の出来事そのもの）や、知らせが届かない端末（アプリの強制停止など）で止まらない。後者だけでも止められるが、次のアラームの時刻まで端末に予定が残る。**どちらか一方では足りず、組み合わせて初めて「消し方を問わず止まる」ようになる**ことは、考察として述べられる。
- 「鳴らす前に確かめる」ことと「時刻どおりに鳴らす」ことはぶつかる。サーバー（Render）が眠っていると答えに1分近くかかるため、答えを長く待つとアラームが遅れる。また、Android では予約したアラームから音を鳴らすサービスを始められるのは時刻から10秒ほどのあいだだけである。そこで「4秒だけ待ち、答えが無ければ鳴らし始め、あとで削除と分かったら止める」とした。**安全側（知らせ損ねない）に倒しながら、止めるべきときは止める**という両立の一つの答えである。
- 端末から確かめるための鍵を、ログインのトークンとは別にした。ログインのトークンは1時間で切れ、使うたびに入れ替わるため、端末のアラームが使うと、アプリの画面のログインと取り合いになる。また、「ログインが切れた」と「アカウントが無い」を区別できなくなる。**認証（その人であること）と、存在の確認（アカウントがまだあること）を分けて考える**必要があった。
- 残る限界：古い版のアプリを使い続けている端末と、削除のあとずっと電波が無い端末は止められない。後者は「通信できないときは鳴らす」という方針の裏返しで、どちらを優先するかは服薬アラームの目的（飲み忘れを防ぐ）から決めた。
