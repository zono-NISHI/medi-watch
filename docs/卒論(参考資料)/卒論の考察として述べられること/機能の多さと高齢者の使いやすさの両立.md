# 機能の多さと高齢者の使いやすさの両立

## 経緯
- 最初は登録時の役割（患者／家族）で画面を分けていた。
- `29bdf4d`（0004）で、1人が「見守る側」と「見守られる側」を兼ねられるようにした。実際の家族関係（自分も薬を飲みながら親を見守る、など）に合わせるためである。
- しかし、すべての利用者に両方の機能を見せると、使わない操作（招待コードの入力、表示の切り替えなど）が画面に増え、高齢の利用者の押し間違いや混乱の元になる。
- そこで `3d874e3`（0005）で、登録時に使う機能を選んでもらい、使わない操作を画面から隠すようにした。
- 見守り画面の家族の切り替えも、プルダウン（`53e01e4`）から2つの大きなボタン（`669b41b`）に作り直した。

## 考察
- 「できることを増やす」ことと「画面を分かりやすく保つ」ことは、しばしば対立する。本アプリでは、機能はすべて実装したうえで、利用者ごとに見せる範囲を絞ることで両立を図った。
- 画面から隠すだけでは、データ上は見守りが続いているのに利用者からは見えない、という食い違いが起こりうる。そのため、ルールは画面だけでなくデータベース（トリガー）でも守るようにした。使いやすさのための工夫が、データの正しさを損なわないよう配慮する必要があった。
- プルダウンは画面を省スペースにできるが、中に何があるか見えず、高齢者には操作が分かりにくい。選択肢が少ないときは、ボタンを並べて常に見えるようにするほうがよいと考えられる。
- 利用者による評価（実際の高齢者に使ってもらうこと）は今後の課題である。

## 補足：見守りの解除を相手に知らせるかどうか
- 見守りを外したことを相手に通知すると、見守っていた人の不安や誤解は減る。一方で、見守られている人にとっては「外したことが相手に伝わる」ため、気軽に外しにくくなる（家族関係に気をつかう）という面もある。
- 本アプリでは、見守る側が状況を把握できることを優先して通知することにし、そのかわり外す側の確認ダイアログで「相手にお知らせが届く」ことを事前に示した。知らせるかどうかを利用者が選べるようにする案もあるが、高齢の利用者には選択肢が増えるほど分かりにくくなるため、今回は採用しなかった。

## 補足：選択肢の「同列に並べる」ことの落とし穴
- 内部では「見守る」「見守ってもらう」の2つの独立したスイッチで設定しているのに、登録画面ではそれを「使い方」という1つの選択に置き換えていた。1つの選択にしたこと自体は、高齢の利用者に2つのスイッチを考えてもらうより分かりやすい。
- ただし、全員が使える基本機能（お薬の記録）を選択肢の1つ（「自分のお薬の管理だけ」）として並べると、他の選択肢ではその機能が使えないかのような誤解を生む。選択肢を同列に並べるときは、それぞれが同じ種類のもの（ここでは「家族とのつながり方」）になっているかを確かめる必要がある。
- 全員に共通することは選択肢の外に一度だけ書き、選択肢では違いだけを示すほうが、文章も短くなり誤解も減ると考えられる。

## 補足：使い道のない入力欄（マイページの「電話番号（任意）」）
- マイページには「電話番号（任意）」の欄があり、入力すると `profiles.phone` に保存される。しかし、2026年11月時点ではアプリのどこにも使われていない（家族の画面にも、通知にも出ない）。初期の設計（0001）で「緊急連絡先」として用意したまま、使う機能が作られなかった。
- 使われない入力欄は、利用者に「入れないといけないのか」「誰に見られるのか」という迷いや不安を与える。特に電話番号は個人情報であり、使い道を説明できないまま集めるのは、必要最小限の個人情報だけを扱うという考え方にも反する。
- 「見守っている家族の画面に、緊急時の連絡先として表示する」などの使い道を作るか、使い道がないなら欄をなくすか、どちらかに決める必要がある。
- 結論として、欄をなくすことにした（2026年11月）。家族はもともと互いの連絡先を知っていることが多く、アプリで電話番号を共有する必要性は低い。入力欄を消すとともに、API（`PATCH /api/auth/me`）でも電話番号を受け付けないようにし、画面以外の経路からも集めないようにした。
- ただし、DBの `profiles.phone` の列は削除していない。列を消すと、すでに入力されていた値が元に戻せない形で失われるためである。使わなくなった列を残すか消すかは、データを消すことの取り返しのつかなさと、不要な個人情報を持ち続けることの危うさとの比較になる。保存済みの値を消す場合は、利用者へ知らせたうえで別のマイグレーションとして行うのが望ましいと考えられる。
