# 仕様書から推測した実装と、実データとの差について

## QRコード（JAHIS形式）の解析で起きたこと
- 当初のパーサーは、仕様書を参考に「薬の情報は1行にまとまっている」と推測して作った。しかし実際の明細書のQRコードでは、薬品（`201`）・用法（`301`）・用法補足（`311`）が別々の行に分かれ、「RP番号」で互いに結び付けられていた。そのため、文字は正しく読めていても薬を1件も取り出せなかった。
- 文字コード（Shift_JIS）の問題と、レコードの構造の問題が重なっていた。前者を解決するまで後者は見えなかった。実データで1段ずつ確かめることの大切さが分かった。

- 1回読み取れたことで「カメラでの読み取りは問題ない」と判断していたが、実際には解像度が足りず、たまたま読めていただけだった。読み取りの成功が環境（カメラの性能・明るさ・距離）に左右されるため、1回の成功で動くと判断せず、何度か試す必要がある。
- 解像度を上げてもノートPCでは読めず、スマートフォンではすぐに読めた。ソフトウェアで改善できる範囲には限りがあり、カメラのピントといった端末のハードウェアの性能にも左右される。お薬手帳のQRコードを読み取る機能は、スマートフォンでの利用を前提に設計するのが妥当だと考えられる。また、カメラで読めない端末のために、内容を貼り付ける方法などの代わりの手段を残しておくことも重要である。

## 考察として述べられること
- 外部の規格に合わせたデータを扱う機能は、仕様書だけでは実装を確定できない。規格のバージョン（今回は JAHISTC06）や、出力するシステム（薬局・医院）によって、項目の使い方に差がある可能性がある。
- 今回確かめたのは1つの医院の明細書だけである。ほかの薬局のQRコードや、別のバージョンのデータで同じように読めるかは確認できていない。今後の課題として、複数の実データで確かめることが挙げられる。
- 正しく取り出せたデータでも、利用者にそのまま見せてよいとは限らない。用法名称には「分1」のような薬局の略語が入っており、開発者自身も意味が分からなかった。専門職向けのデータを一般の利用者（特に高齢者）に見せるときは、言い換えの工夫が必要である。今回は「分N」と回数の幅の順番だけに対応したので、ほかの薬局で使われる略語（「頓用」「外用」など）にも対応できるかは今後の課題である。
- 実データには患者名・生年月日・住所などの個人情報が含まれる。確認用のログを本番に一時的に出す方法は手軽だが、確認が終わったらすぐに消すといった運用上の配慮が必要である。
- 読み取った結果をそのまま登録せず、確認画面で利用者が直せるようにしている。解析が不完全な場合の安全策として有効だと考えられる。
