# 相互見守りの仕組みの工夫

## 1. 1つのアカウントで「見守る側」と「見守られる側」を兼ねられるようにした
- 関連コミット: `29bdf4d`（マイグレーション `0004_mutual_watch.sql`）
- 以前は登録時の役割（患者／家族）で表示する画面を分けていたため、例えば「自分も薬を飲んでいて、親の服薬も見守りたい」人が使えなかった。
- テーブル構造とRLSがもともと役割に依存していなかったことに着目し、作り直すのではなく、不足していた点だけをマイグレーションで補った。
  - 1人が持てる見守りグループ（招待コード）は1つまでにする。
  - 自分の招待コードで自分のグループに参加できないようにする。
  - 見守りの解除（本人の退出、見守られる側による解除）をできるようにする。
  - 映像を見てよいかどうかは、見守られる側だけが変更できるようにする。
- 既存のデータに重複グループがあるとマイグレーションが止まるようにし、データを壊さずに移行できるようにした。

## 2. 使う機能を利用者ごとに選べるようにした
- 関連コミット: `3d874e3`（マイグレーション `0005_watch_features.sql`）
- `profiles.can_watch`（家族を見守る）と `can_be_watched`（家族に見守ってもらう）のフラグを追加した。「自分のお薬の管理」は全員が使う基本機能なのでフラグを持たない。
- 既存の利用者は、これまでどおり両方使える状態で移行した。
- 制約違反はデータベースのトリガーが `HINT` に識別子を入れて返し、サーバーがそれを `code` と利用者向けの日本語に変換する。画面・API・データベースのどこから操作しても同じルールが守られる。

## 3. 見守りを外されたことを、外された人へ通知で知らせるようにした
- 以前は、見守られている本人が「見守りを外す」を押しても、見守っていた人には何も知らされなかった。見守っていた人から見ると、急に相手の情報が表示されなくなるため、「アプリの不具合」や「相手に何かあったのでは」と誤解するおそれがあった。
- 外された人の端末へ「見守りが終了しました：○○さん」というプッシュ通知を送るようにした。
  - 通知を送るのは、見守られている本人が外した場合だけにした。見守っている人が自分で「見守りをやめる」を押した場合は通知しない（見守られている側の生活に影響しないため）。
  - サーバーは、削除した行の `user_id` が操作した本人と違い、かつ削除した行のグループが操作した本人のグループであることを確かめてから通知する。「誰が外したか」をフロントの申告ではなくDBの結果で判断している。
  - 外された人はもう相手の情報を見られないため、通知をタップしたときは相手のホーム画面ではなく、見守り画面を開くようにした（通知に開く画面の `url` を持たせ、Service Worker がそれを優先する）。
  - 外す側にも、確認ダイアログで「相手に通知が届く」ことを示した。黙って通知が送られることがないようにするため。
  - 通知の送信は解除の応答を返した後に行い、通知に失敗しても解除自体は成功として扱う。
- 文言は「○○さんが、あなたによる見守りを外しました。」とした。「あなたの見守りを外しました」では、「あなたが見守ること」と「あなたが見守られること」のどちらとも読めてしまうため。
