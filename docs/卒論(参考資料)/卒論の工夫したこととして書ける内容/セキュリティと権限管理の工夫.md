# セキュリティと権限管理の工夫

## 1. データの閲覧権限をデータベース側（RLS）で守る
- Supabase（PostgreSQL）の Row Level Security（RLS）を使い、「本人」と「見守りを許可された家族」だけが服薬記録などを見られるようにした。
- サーバーのAPIは、ログインした利用者の権限で動くクライアント（`createUserClient(token)`）からデータベースにアクセスする。そのため、APIの書き方を間違えても、権限のないデータは返らない（二重の防御）。

## 2. RLSポリシーの無限再帰（エラー 42P17）を解消した
- 関連コミット: `75adfa8`（マイグレーション `0003_fix_rls_recursion.sql`）
- 問題: 「見守りグループのメンバーなら閲覧できる」といったポリシーが、互いのテーブルを参照し合ったため、PostgreSQL がポリシーの評価を無限にくり返してエラーになった。
- 工夫: 権限の判定を `SECURITY DEFINER` のヘルパー関数（`is_group_member`, `can_view_patient`, `can_view_patient_video` など）にまとめた。ポリシーからはこの関数を呼ぶだけにして、テーブル同士が参照し合わない形にした。
- 以後のマイグレーションでも同じ方式でポリシーを追加するルールにしている。

## 3. 服薬映像の閲覧権限を服薬記録と切り離した
- 関連: `0004_mutual_watch.sql`
- 家族は服薬の「記録」は見られるが、「映像」は見られる人を見守られる側が決められるようにした。映像は Storage のポリシーで、権限のある人だけに限定している。
- 見守り相手の名前は、必要な列だけを返す RPC（`list_my_watchers` / `list_my_watching`）で取得し、`profiles` テーブル自体は「自分のみ参照」のままにした（取得できる個人情報を最小限にした）。

## 4. 管理者権限のクライアントに利用者のセッションが混ざらないようにした
- 関連コミット: `9b0cd51`（`src/supabase/supabase.js`）
- 問題: supabase-js はクライアントの中にログイン状態（セッション）を保持する。RLSを無視できる管理者用クライアント（`supabaseAdmin`）でログイン処理をすると、以後の通知処理などが「最後にログインした利用者」の権限で動いてしまう。また、認証用クライアントを全リクエストで共有すると、同時に来た別の利用者のセッションと混ざる恐れがある。
- 工夫: クライアントを3種類に分け、用途を決めた。
  - `supabaseAdmin`: cron・通知処理専用。ログイン処理は呼ばない。
  - `createAuthClient()`: サインアップ・ログインなどの認証処理用。リクエストごとに新しく作る。
  - `createUserClient(token)`: 利用者の権限でRLSを適用して使う。

## 5. ログやURLに使い捨てトークンを残さない
- メール確認・パスワード再設定の画面（`verify-email.html` / `reset-password.html`）のURLには使い捨てのトークンが含まれるため、アクセスログ（Morgan）にはクエリ文字列を伏せて記録するようにした。

## 6. エラーの内容を利用者に見せすぎない
- 関連コミット: `75adfa8`（`src/lib/utils.js` の `sendSupabaseError`）
- 以前はデータベースのエラーメッセージをそのまま画面に返していた。PostgreSQL のエラーコードを見て、「権限がない（403）」「すでに登録されている（409）」「サーバーの設定不備（500）」などに分類し、利用者には平易な日本語だけを返すようにした。内部の情報（テーブル名やポリシー名）が外に漏れるのも防げる。
- フロントエンドは文言ではなく `code` で処理を分けるので、文言を変えても動作が壊れない。

## 7. 見守りを外した人が、同じ招待コードで戻ってこられないようにした
- 関連: `0006_regenerate_invite_code.sql`、`src/routes/careGroups.js`、`public/js/pages/family.js`
- 問題: 招待コードは初めて発行したときに1度だけ決まり、その後は変わらなかった。そのため、見守られる人が「見守りを外す」を押しても、外された人は以前に教わったコードを入力すれば、また見守りを始められてしまった。招待コードは「合言葉」として働いているので、一度知った人がずっと使えるのは、外したという本人の意思に反する。
- 工夫:
  - 見守られる本人が「見守りを外す」を行ったときに、データベースのトリガーで招待コードを新しいランダムな値に作り直すようにした。API の処理ではなくトリガーで行うので、どの経路で削除しても作り直しが漏れない。見守る人が自分で「見守りをやめる」を行ったときは、本人の意思で離れただけなので作り直さない（ほかの家族に伝えたコードが無駄にならない）。
  - コードを伝える相手を間違えたときのために、本人が「新しい招待コードにする」を押していつでも作り直せるようにした。
  - 見守りの関係は `care_group_members` の `group_id` で結び付いているので、コードを作り直しても、すでに見守っている家族の見守りは切れない。
  - コードは `gen_random_uuid()` の乱数部分（暗号学的に安全な乱数）から作り、ほかのグループと重ならない値になるまで作り直す。
