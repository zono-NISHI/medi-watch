# Web版とネイティブ版で画面とサーバーを共有する工夫

## 背景
- Web アプリ（PWA）では、アプリを閉じているとき・ロック中・ほかのアプリを使っているときに、服薬アラームを鳴らせない（`卒論の考察として述べられること/Webアプリ（PWA）で服薬を知らせることの限界.md`）。
- 一方で、画面をすべてネイティブで作り直すと、Web 版と2つの画面を管理することになり、手間も不具合の元も倍になる。

## 工夫したこと
- **画面は1つ、届け方は2つ。** Capacitor を使い、Web 版の `public/` をそのまま Android アプリに同梱した。ネイティブで新しく作ったのは、アラームの部分（`mobile/android/app/src/main/java/jp/mediwatch/app/alarm/`）だけである。お薬の登録・記録・見守りなどの画面は、Web 版を直せばネイティブ版も直る。
- **画面をアプリに同梱する方式（Render の URL を開く方式にしなかった）。**
  - アラームから「カメラを起動する」を押したとき、画面はスマホの中から開くので、電波が弱くても、Render の無料プランがしばらく止まっていても、すぐ撮影画面が出る。
  - 同梱した画面はスマホの中（`https://localhost`）から開くため、サーバーとはオリジンが違う。そこで、`config.js` でアプリの中かどうかを判定して API の宛先を切り替え、サーバーには、アプリのオリジンだけを許可する CORS の設定を追加した（`server.js`）。認証は Cookie ではなく Authorization ヘッダーのトークンで行っているため、オリジンを許可しても、ほかのサイトから利用者になりすました操作はできない。
- **Web の画面とネイティブのアラームの役割分担。**
  - Web の画面（`alarm.js`）は、これまでどおりサーバーから予定と今日の記録を取得し、それを `NativeAlarm.sync()` で端末に渡す。端末側は予定を保存し、次に鳴らす時刻を1つだけ `AlarmManager.setAlarmClock` で予約する。
  - アプリを閉じていても鳴らせるよう、予定は端末に保存しておき、再起動後や時刻の変更後にも予約し直す（`BootReceiver`）。
  - 服薬時刻より前にアプリで記録した予定は、端末に「今日は済み」と伝えて鳴らさない。鳴っている最中に記録した場合も止める。
  - アラームの「カメラを起動する」は、Web 版のアラームと同じ入り口（`home.html?take=スケジュールID`）を開くようにした。撮影の処理を二重に作らずに済んだ。
  - ネイティブ版では音を端末のアラームが鳴らすので、Web の画面のアラームは音を出さないようにした（同時に鳴って聞き取りにくくなるのを防ぐ）。ただし通知が許可されていないときは、これまでどおり Web の画面で鳴らす。
- **サーバーの依存関係に影響させない。** ネイティブ版は `mobile/` に別の `package.json` を置き、Render が使うルートの `package.json` には Capacitor を入れていない。本番サーバーのビルドが重くなったり壊れたりしない。
- **高齢の利用者への配慮。** アラーム画面は、Web 版と同じ色（藍色・テラコッタ）で、「カメラを起動する」を画面の残りの高さをすべて使う大きなボタンにした。戻るボタンでは閉じず、ボタンで選んでもらう。アラームに必要な4つの許可は、マイページに「済み ✓／設定する」の一覧で表示し、押すとその設定画面が直接開くようにした。
- **音量を下げても、上げればまた聞こえるアラーム（2026-11-16）。** 最初は通知の音でアラームを鳴らしていたが、音量を一度0にすると、上げても鳴らなくなった。音と振動をアプリ自身で鳴らす（`AlarmSound`・`AlarmSoundService`）ように作り直し、音量0のあいだも再生を続けて、上げればその場で聞こえるようにした。あわせて、アラームの画面で音量ボタンを押したときは着信音量ではなく「アラーム」の音量が変わるようにし（押しても鳴っている音が変わらない、という混乱を防ぐ）、通知を横に払って消したときは「あとで」と同じく5分後に鳴らし直すようにした（うっかり消して飲み忘れる、を防ぐ）。
- **撮影画面を記録せずに閉じたら「あとで」と同じにする（2026-11-16）。** 利用者の意見から、2つの問題が見つかった。(1) アラームの「カメラを起動する」を押すと、撮影画面が開く前に、アプリ内（Web の画面）のアラームが一瞬出ていた。ホームを読み込んだ直後は「未記録の予定がある」状態なので、撮影画面より先に Web のアラームが判定されていたためである。撮影画面を「×」で閉じると、この画面にまた戻り、似たボタンが並ぶ画面を行き来することになっていた。(2) 端末のアラームは「カメラを起動する」を押した時点で止まり、同じ服薬時刻では二度鳴らさない作りだったので、「×」で閉じてアプリを離れると、記録しないまま、その日はもう知らせが来なかった。
  - 対応: アラームから来たときは、撮影画面を開くまで Web のアラームを出さないようにした。撮影画面を記録せずに閉じたときは、「あとで」と同じ扱いにして「5分後にもう一度お知らせします」と伝え、端末のアラームを5分後に鳴らし直す（プラグインに `snooze` を追加。どの予定を鳴らし直すかは、端末側にはもう残っていないので、Web の画面から服薬時刻と一緒に渡す）。
  - 音についての判断: 撮影画面では音も振動も出さない。利用者はすでに気付いて操作しており、鳴り続けると急かされ、読み上げの案内も聞き取りにくくなるためである。「操作中は静かに、放置されたら鳴り直す」と役割を分けた。
  - Web とネイティブの2つのアラームが、同じ予定をそれぞれ別に判定している。共有の利点（画面を二重に作らない）の裏で、「片方を止めても、もう片方が出る」「片方を止めたら、もう片方も二度と鳴らない」という食い違いが起きやすいことが分かった。
- **ネイティブのアラーム画面を、Web のアラーム画面と同じ見た目にそろえた（2026-11-17）。** 「お薬の時間です」の画面は、Web の画面（`alarm.js`）と、端末のアラーム（Java の `AlarmActivity`）の2か所で別々に作っている。初めは、端末のアラームを濃い藍色の背景に白い文字、Web の画面を明るい紙色の背景に藍色の文字にしていた。しかしネイティブ版では、端末のアラームで1つ目のお薬を記録した直後に、Web の画面のアラームが残りのお薬を知らせる。同じ「お薬の時間です」なのに色も形も違うと、利用者には別のお知らせに見える。開発者が実際に両方を見比べて、この違いに気付いた。
  - 対応: 端末のアラームを、Web の画面と同じ配色（紙色の背景・藍色の文字・テラコッタのボタン）・同じ並び順（ベルの印 → いまの時刻 → 予定の時刻 → お薬の名前 → カメラのボタン → あとで）・同じ文字の大きさにした。ベルとカメラの印は、Web の SVG と同じ形をベクター画像として持たせ、ベルが揺れる動きも同じ角度・同じ周期で再現した。
  - そろえなかった点とその理由: (1) ボタンの種類。端末のアラームはロック中にも出る画面で、ログインの情報を持たないため、「映像なしで記録」などサーバーに記録するボタンは置けない。(2) 画面上部に重ねて出す帯。ほかのアプリの画面の上に出すので、どんな背景でも見分けられるよう濃い藍色のままにした。「同じ見た目にする」ことより、「その場面で確実に目に入る・安全に動く」ことを優先した。
  - （同日の変更）(1) の「映像なしで記録」は、置き方を変えて端末のアラームにも置いた。端末のアラームの画面は、いまもログインの情報を持たず、自分ではサーバーに記録しない。ボタンを押すと、ロックを解除してアプリのホームを開き（`home.html?record=スケジュールID`）、Web の画面が記録する。「カメラを起動する」と同じ形の入り口を1つ足しただけで、記録の処理は二重に作っていない。お薬が2つ以上のときは、ホームを開くだけにして、Web の画面のアラーム（お薬ごとのボタン）で選んでもらう。
    - 「開いただけで記録される入り口」には、2つの歯止めを付けた。ブラウザ版では受け付けない（細工したリンクを開かせるだけで「飲んだ」と記録させられるのを防ぐ）。ネイティブ版では、押してから1分を過ぎた頼みは実行しない（Android は、終了したアプリを履歴から開き直すときに、前と同じ頼みをもう一度渡すことがある。そのまま実行すると、別の日に、押していないのに「飲んだ」と記録されてしまう）。
  - （同日の変更）ベルの印は、そのあと Web・ネイティブの両方から外した。片方だけ外すと、そろえた見た目がまた食い違うので、2か所を同じ作業の中で直した（理由は `高齢の利用者に向けた画面と操作の工夫.md` の「アラームの画面から、飾りのベルの印を外した」）。
  - 画面を共有する方式でも、共有できない部分（アプリを閉じているときに出す画面）は二重に作ることになる。二重に作った部分は、片方だけを直すと見た目が食い違っていく。色・余白・文字の大きさの値を Web の CSS と同じ数字で書き、コメントに対応する CSS の場所を残して、次に直すときに両方を直せるようにした。

- **開発環境を別のパソコン・スマホで再現できるようにした。** 生成物（`node_modules/`、`npx cap sync` が `public/` からコピーする画面、Android Studio の個人設定など）は Git に入れず、ソースコードだけを管理している。その代わり、パソコンやスマホを変えたときに「どの手順をやり直す必要があるか」を `mobile/README.md` に表でまとめた。実際に作業して詰まった点（スマホが認識されない、Gradle と Java のバージョンが合わない、新しいパソコンに Node.js が入っておらず `npm` が見つからない）も、対処の手順として残した。インストーラーの途中で迷う選択肢（Node.js の「Tools for Native Modules」）についても、このプロジェクトの依存パッケージはすべて JavaScript だけで書かれていてコンパイルが要らないことを確かめたうえで、「チェックを入れずに進める」と理由つきで書いた。署名用の鍵は作り直すと更新版を入れられなくなるため、作り直さずに引き継ぐことを明記した。さらに、作業を一時終了するときの手順（`mobile/開発を一時終了するときの手順.md`）もまとめた。アラームは端末に予約されるため、アプリや Android Studio を閉じても鳴り続ける。テスト用に登録したお薬を消し忘れると、毎日鳴ってしまう。この点を、終了時の確認項目に入れた。また、変更の種類（Java・Web の画面・API）ごとに「Render へのデプロイで反映されるか」「`npx cap sync` が要るか」「APK の作り直しが要るか」が違って迷いやすい。そこで、AI（Claude Code）への指示書（`CLAUDE.md`）に「作業のたびに、このあと開発者がすること（Android Studio で Run を押す、develop へマージして Render のデプロイを待つ など）を示す」というルールを加え、変更のたびにその場で案内されるようにした（2026-11-16）。手順書を別に作って保守するより、変更内容に合った手順を毎回示すほうが、手順書が古くなる心配がない。

- **パソコンごとの設定を Git に混ぜない。** Android Studio は、プロジェクトを開くだけで `.idea/` の中のファイル（使う JDK の名前、選んだスマホなど）を書き換える。初めはその一部をコミットしていたため、別のパソコンで開くたびに「変更あり」になり、コミットしてよい変更と、してはいけない変更を毎回見分ける必要があった。ビルドに必要な設定はすべて Gradle のファイルにあり、`.idea/` がなくてもビルドできる。そこで `.idea/` を丸ごと Git の管理から外した。開発者が増えても、互いの環境の設定を上書きし合わずに済む。

- **同じお知らせを、端末に合った仕組みで届ける（2026-11-17）。** ネイティブ版の画面（WebView）は Web Push に対応していないため、ネイティブ版を使う家族には「飲み忘れ」などのお知らせが届かなかった。そこで、ネイティブ版には Firebase Cloud Messaging（FCM）で届けるようにした。
  - **送る側（サーバー）は1か所で振り分ける。** 端末の宛先を保存する表（`push_subscriptions`）に「種類」の列（`webpush` / `fcm`）を足し、FCM の宛先（トークン）は Web Push の宛先と同じ列に入れた（マイグレーション `0007_fcm_push.sql`）。送信処理（`notificationService.js` の `sendToSubscription`）が種類を見て、Web Push なら `web-push`、FCM なら `firebase-admin` で送る。「誰に・いつ・何を送るか」（cron の飲み忘れの判定、見守っている家族の取り出し、二重送信を防ぐ `notification_logs`）は1行も変えずにそのまま使えた。同じ端末の二重登録を防ぐ一意制約と、「自分の端末しか操作できない」RLS も、同じ列を使うので FCM にもそのまま効く。
  - **受け取る側（画面）も1か所で切り替える。** 通知を有効にする処理（`push.js` の `PushSetup`）の中で、ネイティブ版かどうかを判定して Web Push と FCM を切り替えた。各画面は「有効にする」「この利用者に結び付け直す」「ログアウト時に外す」を呼ぶだけで、どちらの仕組みかを知らなくてよい。バンドラーを使わない構成のため、Capacitor の通知プラグインは、Capacitor が画面に用意する `nativePromise`・`addListener` で直接呼んだ（Capacitor 本体のコードを読んで、この方法で使えることを確かめた）。
  - **二重に知らせない。** ネイティブ版では、自分のお薬の時間は端末のアラームが知らせる。サーバーからの「お薬の時間です」まで届くと、同じことを2回知らせることになる。そこで、cron のリマインドは Web Push の端末だけに送り、FCM の端末には家族向けのお知らせ（服薬完了・服薬映像・飲み忘れ・見守りの終了）だけを送るようにした。
  - **操作を増やさない。** ネイティブ版では、アラームのために通知の許可をすでにもらっていることが多い。許可があれば、ホームかマイページを開いたときに自動で FCM に登録するので、アプリを新しい版にするだけで家族のお知らせが届くようになる。通知は「ご家族のお知らせ」という専用の通知チャンネルで出し、スマホの設定でアラームとは別にオン・オフできるようにした。
  - **古い版のアプリでも壊れない。** 通知プラグインが入っていない古い版のアプリでは、プラグインを呼ぶとエラーになる。画面側で、アプリに入っているプラグインの一覧（`Capacitor.PluginHeaders`）を見てから呼ぶようにし、古い版では「アプリを新しい版に更新してください」と案内する。サーバー側も、Firebase の鍵が未設定でも起動を止めず、アプリへの通知だけを送らないようにした。

## 卒論での書き方の例
- 「1つのコードから、インストール不要の Web 版と、確実に知らせる Android 版の2つを提供した。ネイティブで実装したのはアラームの部分（Java で約1,000行、コメントを含む）だけで、残りの画面・サーバー・データベースは共通である。」

## 確認メールのボタンから、アプリの画面へ戻す工夫

- 課題: アプリ（Android のネイティブ版）で新規登録すると、確認メールのボタンはブラウザで開くため、確認がブラウザの中で済んでしまい、アプリの画面は「メールをご確認ください」のまま残っていた。高齢の利用者には、どちらの画面を使えばよいか分かりにくい。
- 工夫1: 登録のとき、どこから登録したか（`android` / `web`）をサーバーが決まった値だけで user_metadata に入れ、メールのテンプレートがボタンのリンクに `client=android` を付ける。利用者の自由入力をメールに差し込まない方針は守っている。
- 工夫2: ブラウザで開いた確認画面は、アプリで登録した人が Android で開いたときだけ「アプリで確認を完了する」ボタンを出す。ボタンは Android の `intent:` リンクで、アプリ独自の `mediwatch://verify-email?token_hash=…` を開く。アプリが入っていなければ、ブラウザの通常の確認画面に切り替わる（`browser_fallback_url`）。
- 工夫3: アプリ側（MainActivity）は受け取った値の形を確かめてから、アプリの中のメール確認画面を開き直し、その画面がそのまま確認を済ませてホームへ進む。ブラウザの画面でボタンを押す操作をしているため、アプリでもう一度押させない。一方、メールを開いただけ（メールのセキュリティ機能の先読み）では確認しない、という元の作りは保っている。
- Web 版の確認画面（verify-email.html）をそのままアプリに同梱して使い回しているので、アプリ用の画面を別に作らずに済んだ。
- 工夫4: アプリへ移ったあと、メールアプリ（Gmail）が開いたブラウザの画面が残ると、戻ったときに確認ボタンの画面が見えて迷わせる。そこで、アプリが前に出て確認画面が裏に回ったら、スクリプトでその画面を閉じる（`window.close()`）。ブラウザが閉じるのを許すのは、戻る履歴の無い画面などに限られ、確実ではない。そのため、閉じられなかったときは「この画面は閉じてかまいません」という表示に切り替えておき、どちらになっても利用者が迷わないようにした。押した瞬間ではなく裏に回ってから閉じるのは、アプリが開く前に画面が消えるのを避けるため。
