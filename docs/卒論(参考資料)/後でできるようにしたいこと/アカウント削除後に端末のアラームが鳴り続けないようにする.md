# アカウント削除後に端末のアラームが鳴り続けないようにする

> **実装済み（2026-11-26）**：下の「作り方の案」の案A・案B・案C（相当）をすべて組み合わせて作った。
> - 案B：アラームを鳴らす前と、アプリを開いたときに、端末がサーバーへアカウントの有無を確かめる（`AlarmAccount`・`POST /api/auth/alarm-status`）。鍵はログインのトークンとは別の、アラーム用の鍵（`src/lib/alarmKey.js`）。
> - 案A：マイページの「アカウントを削除する」（`POST /api/auth/delete-account`）。削除後に FCM のデータメッセージ `account_deleted` を送り、端末の `AccountMessagingService` が受け取って止める。
> - 案C：アプリを開いたときの確認は、画面（JavaScript）ではなく Java 側（`MainActivity.onStart`）で行う形にした。
> - 「4. 端末に残すデータを誰のものかと結びつける」も一部実施（鍵と一緒にユーザー ID を保存し、別のアカウントの知らせでは消さない）。
> - 見送ったもの：1日1回の定期確認（WorkManager）。鳴らす前に必ず確かめるため、「鳴ってしまう」ことは防げる。ただし、次のアラームの時刻までは、端末に予定（お薬の名前）が残る。「削除予定」の猶予期間、ロック画面でお薬の名前を隠す設定、届かなかった件数の監視も見送った。
> - 防げないもの：古い版の APK を使い続けている端末。アカウントの削除のあと、ずっと電波が無いままの端末（安全のため、確かめられないときは鳴らす作りのため）。


開発中に Supabase の SQL Editor で `DELETE FROM auth.users;` を実行し、アカウントをすべて削除したところ、ネイティブ版（Android）を入れたスマホで服薬アラームが鳴り続けた出来事から出た案。スマホをタイムロッキングコンテナ（時間が来るまで開かない容器）に入れていたため、手で止めることもできなかった。

## 現状
- ネイティブ版は、最後に取得したお薬の予定を端末の中に保存している（`AlarmStore`）。アラームが鳴るたびに、保存した予定から次の服薬時刻を予約し直す（`AlarmScheduler.reschedule`）。電源を入れ直したときも予約し直す（`BootReceiver`）。
- 端末のアラーム（`AlarmScheduler`・`AlarmRinger`・`AlarmActivity`）はサーバーと一切通信しない。鳴らすかどうかは、端末に保存した予定だけで決めている。
- 保存した予定が消えるのは、次の2つのときだけ。
  1. マイページで「ログアウト」を押したとき（`public/js/pages/mypage.js` の `NativeAlarm.clear()`）
  2. アプリの画面が予定を取得でき、その中身が空だったとき
- アカウントがサーバーで消されると、アプリの画面は予定を取得できず（401）、ログイン画面へ移るだけで `NativeAlarm.clear()` は呼ばれない（`public/js/api.js` の `redirectToLogin`）。
- そのため、端末に残った予定は消える機会がなく、**同じ時刻に毎日鳴り続ける**。1回のアラームは服薬時刻から最長60分で自動的に止まる（`AlarmStore.ALARM_WINDOW_MS`）。
- アプリがログインの無効に気づくのは、利用者がアプリの画面を開いてサーバーに問い合わせたときだけ。利用者が何もしなければ気づかない。
- サーバーから端末へ「止めて」と伝える手段もない。通知の宛先（`push_subscriptions`）はアカウントの削除と一緒に消える（CASCADE）。
- Web 版は、ログインが切れると予定を取得できずアラームが出ないため、この問題は起きない。

## なぜ直すべきか
- **利用者を混乱させる**：消したアカウントのお薬の時間を知らせ続ける。高齢の利用者なら「まだ飲む薬があるのか」と思い、飲む必要のない薬を飲んでしまうおそれがある。
- **個人情報が残る**：アカウントを消しても、端末のアラーム画面や通知にお薬の名前が出続ける。
- **一般的な作り方と違う**：多くのアプリは、ログインが無効になったと分かった時点で、端末に保存したデータや予約した通知・アラームも消す。
- **ストアの決まり**：Google Play は、アカウントを作れるアプリに削除の手段を求めている。削除後にその人のデータで端末が動き続けるのは望ましくない。

## 気をつけたいこと（作るときの課題）
1. **「止めるべきとき」と「止めてはいけないとき」を区別する**（いちばんの課題）
   - ログインが切れただけで黙ってアラームを止めると、高齢の利用者が気づかないまま飲み忘れが続く。
   - 「`redirectToLogin()` で `NativeAlarm.clear()` を呼ぶ」だけの修正は、期限切れのときまで止めてしまうため、それだけでは不十分。
   - 端末の扱いは、サーバーの答えによって次のように分ける。

     | サーバーの答え | 端末の扱い |
     |---|---|
     | 「アカウントは削除された」とはっきり分かる | 予定を消して、鳴らさない |
     | 通信できない・サーバーの障害 | いつもどおり鳴らす（電波が無いだけで知らせ損ねるのは危険なため） |
     | ログインの期限切れ（アカウントはある） | 鳴らし続けたうえで、「ログインし直してください」と案内する |

2. **利用者が何もしなくても止まるようにする**
   - アプリを開いたときに消すだけでは、今回のようにスマホを触れない状況では止まらない。
3. **ネイティブ側に通信の仕組みが無い**
   - 端末からサーバーへ確かめるには、Java 側に通信の処理と、そのための鍵（トークン）の受け渡しが必要になる。
4. **ネイティブ版の手間**
   - `public/` を変えたあと、`npx cap sync android` と APK の作り直しが必要。

## 実際に多くの人が使うシステムなら、どうするか
「消し方」と「気づき方」の両方を何重にも用意する。

### 1. アカウントの削除は、決まった手順を通してだけ行う
- SQL で `auth.users` を直接消すことは、運用では行わない。アプリ・サーバーの「アカウント削除」の処理を通して消す。
- その処理の中で、次の順に後始末をする。
  1. その人の端末の一覧（`push_subscriptions`）を読み出す
  2. 各端末へ「データを消して」という知らせを送る（下の 2.）
  3. 映像（Storage の `medication-videos`）などの関連データを消す
  4. 最後にアカウントを消す
- すぐには消さずに「削除予定」の状態にして、数日〜30日後に完全に消すことが多い（誤操作や、乗っ取りによる削除への備え）。
- Google Play では、アプリ内と Web の両方から削除できる手段を用意することが求められている。

### 2. サーバーから端末へ知らせる（利用者が何もしなくても止まる）
- 削除したときや「すべての端末からログアウト」したときに、FCM のデータメッセージ（画面に出ない通知）を送る。端末は受け取ったら、アラームの予約と保存した予定を消す。
- 電源が切れていた端末にも、電源が入ったあとに届く（FCM が一定期間取っておくため）。
- ただし届かないこともあるので、これだけには頼らない（3. と組み合わせる）。
- SQL で直接 `auth.users` を消すと、宛先の情報も同時に消えるので送れない。

### 3. 端末からも定期的に確かめる
- ネイティブ側で、1日1回ほど（WorkManager など）と、アラームを鳴らす前に、サーバーへ「このアカウントの予定はまだ有効か」を問い合わせる。
- 結果の扱いは、上の「気をつけたいこと」1. の表のとおりに分ける。
- 端末には、アラームの予定を確かめるためだけの、長く使える端末用の鍵を渡すことが多い（ログインのトークンとは別にする）。

### 4. 端末に残すデータを「誰のものか」と結びつける
- 保存する予定に、アカウントの ID を一緒に記録する。別の人がログインしたら、前の人の予定は消す。
- ロック画面に出す内容は「お薬の時間です」までにし、お薬の名前は出さない設定を選べるようにする（端末を他人が見る場合への配慮）。

### 5. 運用面
- 削除の知らせが端末まで届いたかを記録し、届かなかった件数を監視する。
- 「削除後にアラームが鳴らないこと」「通信できないときは鳴ること」をテストの項目に入れる。
- 利用者向けに、「アプリを消す前にログアウトしてください」「止まらないときは設定からストレージを消去」といった案内を用意する。

## 作り方の案（このアプリでの落としどころ）

### 案A：アカウント削除をアプリの機能として用意し、削除の前に端末へ知らせる
1. `POST /api/auth/delete-account`（仮）を追加する。`supabaseAdmin.auth.admin.deleteUser` で消す前に、その人の `push_subscriptions`（`kind = 'fcm'`）へ FCM のデータメッセージを送る。
2. ネイティブ版は、そのデータメッセージを受け取ったら `AlarmStore.clearAll()` と予約の取り消しを行う。
3. マイページに「アカウントを削除する」ボタンを置く（確認の画面つき）。
4. `利用者目線のアプリ挙動一覧.md` を更新する。

### 案B：ネイティブ側で、鳴らす前にサーバーへ確かめる
1. サーバーに「このアカウントは有効か」を返す API を用意する（「削除」と「期限切れ」を区別して返す）。
2. Java 側に、鳴らす前（または1日1回）に問い合わせる処理を追加する。「削除」のときだけ予定を消し、通信できないときは鳴らす。
3. 問い合わせに使う鍵を、アプリの画面から `MediAlarm` プラグイン経由で端末に渡す。

### 案C：最小限の対処
- 「ログアウト」のほかに、アプリの画面が「アカウントが存在しない」と分かったときにも `NativeAlarm.clear()` を呼ぶ。期限切れのときは呼ばない。
- アプリを開くまでは鳴り続けるが、開けば止まる。

実用的には、案A と案B の組み合わせが確実。作業量が限られる場合は、案C から始める。

## 手間の目安
- 案A：1〜2日程度。API 1本、FCM のデータメッセージの受信処理（Java）、マイページのボタン。
- 案B：2〜3日程度。Java 側の通信処理と鍵の受け渡し、サーバーの API、通信できないときの扱いの確認。
- 案C：半日程度。

## 卒論での位置づけ
- 作れなかった場合は「今後の課題」として書ける。開発中に実際に起きた出来事（アカウントを消したのに、触れない場所でアラームが鳴り続けた）を例として示せる。
- 「止めるべきとき（アカウントの削除）は確実に止める」と「止めてはいけないとき（通信の不具合・ログインの期限切れ）は止めない」の両立は、服薬アラームならではの設計の難しさとして、考察の材料になる。
- 端末だけで鳴らす作り（通信できなくても鳴る、という利点）が、逆に「サーバーの変更が端末に届かない」という弱点にもなる点も、考察として述べられる。
