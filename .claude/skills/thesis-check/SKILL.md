# 卒論とシステムの照合（調べるだけ）

卒論本文・要旨・発表スライドを読み、現在のシステムと食い違う記述を一覧にして報告する。**このスキルではファイルを書き換えない。** 直すのは `thesis-edit`（Word）と `thesis-slides`（スライド）。

## 手順

1. 対象の文章を書き出す（リポジトリのルートで実行）。
   - 本文・要旨: `python scripts/thesis/dump_docx.py "docs/卒論(参考資料)/最新の卒論、要旨、パワポ/<ファイル>.docx"`
   - スライド: `scripts/thesis/slides/build_slides.js` を読む（スライドの文言とノートがすべて入っている）
2. システムの現状を確かめる。次の順に読むと速い。
   - `利用者目線のアプリ挙動一覧.md`（画面ごとの挙動。ソースと同時に更新している）
   - `CLAUDE.md` の「アーキテクチャ」
   - `git log` で、前回の照合より後のコミット（前回の日付は `scripts/thesis/edits/` のファイル名の日付）
   - 数値や仕様を論文に書いている箇所は、ソースコードで確かめる（例: 通知の種類は `src/services/notificationService.js`、テーブルは `src/supabase/migrations/`）
3. 食い違いを一覧にして報告する。1件ごとに次を書く。
   - どこ（章・節、表の番号、スライドの番号）
   - 論文の記述
   - 現在のシステム（根拠のファイル）
   - 直し方の案

## 範囲を絞る

- 利用者が「前回以降の変更だけ」と言ったら、手順2の `git log` で出たコミットに関係する記述だけを調べる。全体を読み直さない。
- `docs/` の資料は古い記述を含むので、根拠にしない。根拠はソースコードとマイグレーション。

## 自分では決められないこと

次の内容はソースコードから分からないので、推測で書かず、利用者に確かめる項目として挙げる。

- 動作確認をどこまで実施したか（表5.1の「状況」）
- 実施していない検証（iOS、第三者による評価など）
- 反省点・感想など、本人の考えを書く部分
