# 卒論とシステムの照合と、自動の修正

卒論本文・要旨・発表スライドを読み、現在のシステムと食い違う記述や、書き足すべき新しい機能・工夫を見つけたら、**利用者に直す項目を選ばせずに、必要と判断したものをすべて直す。** 直し方は `thesis-edit`（Word）と `thesis-slides`（スライド）の手順に従う。直した結果を見て、手直しが要れば利用者がそのつど指示する。

- 利用者が「調べるだけ」「一覧だけ」「直さないで」と言ったときだけ、手順3の一覧を出して終わる（ファイルは書き換えない）。

## 手順

1. 対象の文章を書き出す（リポジトリのルートで実行）。
   - 本文・要旨: `python scripts/thesis/dump_docx.py "docs/卒論(参考資料)/最新の卒論、要旨、パワポ/<ファイル>.docx"`
   - スライド: `scripts/thesis/slides/build_slides.js` を読む（スライドの文言とノートがすべて入っている）
   - `python` が使えない（Microsoft Store の案内だけが出る、など）ときは、`docs/卒論(参考資料)/最新の卒論、要旨、パワポ/卒論・要旨・パワポを直す手順.md` の「Python を入れる」の手順を利用者に示す。照合のための読み出しだけは、PowerShell で .docx（zip）の `word/document.xml` から `<w:t>` を拾って代用してよい（書き換えには使わない）。
2. システムの現状を確かめる。次の順に読むと速い。
   - `利用者目線のアプリ挙動一覧.md`（画面ごとの挙動。ソースと同時に更新している）
   - `CLAUDE.md` の「アーキテクチャ」
   - `git log` で、前回の照合より後のコミット（前回の日付は `scripts/thesis/edits/` のファイル名の日付）
   - 数値や仕様を論文に書いている箇所は、ソースコードで確かめる（例: 通知の種類は `src/services/notificationService.js`、テーブルは `src/supabase/migrations/`、Java の行数は `mobile/android/app/src/main/java/`）
3. 直す項目を決める。次の2種類を対象にする。
   - **修正**: 論文の記述が、いまのシステムと食い違っているもの（古い文言・数値、もう済んだ「今後の課題」など）
   - **追加**: 前回より後に入った機能・設計の見直しのうち、本文の「工夫」や設計の判断として書けるもの（`docs/卒論(参考資料)/卒論の工夫したこととして書ける内容/` のメモも手がかりにする。ただし事実はソースで確かめる）
   - 同じ内容が本文・要旨・スライドのどこにあるかを洗い出し、まとめて直す。
4. 直す。
   - 本文・要旨は `thesis-edit` の手順（修正内容ファイルを `scripts/thesis/edits/<今日の日付>_<honbun|youshi>.py` に書き、`apply_edits.py` → `finalize.ps1`）で直す。
   - スライドは `thesis-slides` の手順（`build_slides.js` を書き換えて作り直し、画像に書き出して見た目を確かめる）で直す。
   - 要旨は2ページに収める。追加は本文を中心にし、要旨・スライドには、食い違いの修正と、収まる範囲での要点だけを入れる。
   - `python` が無くて Word に適用できないときは、修正内容ファイルまで作って止め、Python を入れたあとで適用するコマンドを示す。スライドは Node.js だけで作り直せるので先に直してよい。
5. 報告する。直した項目ごとに、どこ（章・節、表、スライドの番号）・前の記述・新しい記述の要点・根拠のファイルを短く書く。そのうえで `CLAUDE.md` の決まりどおり、変更したファイルの一覧・コミットメッセージ案・PR 説明文案を示す。git の操作はしない。

## 範囲を絞る

- 利用者が「前回以降の変更だけ」と言ったら、手順2の `git log` で出たコミットに関係する記述だけを調べる。全体を読み直さない。
- `docs/` の資料は古い記述を含むので、根拠にしない。根拠はソースコードとマイグレーション。

## 自分では決められないこと

次の内容はソースコードから分からないので、推測で書かない。

- 動作確認をどこまで実施したか（表5.1の「状況」）
- 実施していない検証（iOS、第三者による評価など）
- 反省点・感想など、本人の考えを書く部分

新しい機能を表5.1の確認内容に足すときや、上の内容に触れる文を書くときは、その部分を `⟦…⟧` で囲んで黄色の蛍光ペンにし（`thesis-edit` を参照）、報告の最後に「確かめたいこと」として挙げる。ほかの項目の修正は止めずに進める。
